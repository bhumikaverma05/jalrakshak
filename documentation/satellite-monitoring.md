# Satellite-based water monitoring foundation

## Current implementation boundary

The repository contains a `satellite_observations` table, read-only observation/history APIs, and a processing foundation for Sentinel-2 Level-2A bands. No live scene search or imagery download provider is configured. The `Sentinel2Provider` protocol defines the seam for a concrete provider without inventing credentials or observations.

Processing accepts co-registered or differently gridded B03, B11, and SCL arrays plus their CRS, affine transform, and nodata values. It projects the water-body boundary to a local UTM zone, aligns reflectance bands with bilinear resampling and SCL with nearest-neighbour resampling, clips to the boundary, masks SCL no-data/defective, cloud-shadow, low-probability/unclassified cloud, cloud, cirrus, and snow classes, and computes:

```text
MNDWI = (B03 - B11) / (B03 + B11)
```

Pixels at or above `SATELLITE_MNDWI_WATER_THRESHOLD` are classified as water. The default threshold `0.0` is a configurable pilot value, not a locally calibrated scientific cutoff. Validate the chosen threshold against reviewed imagery for each relevant water-body type.

Water area is counted on the projected grid in square metres. It is converted to square kilometres before populating `estimated_area_sq_km`; the exact square-metre calculation, threshold, pixel size, CRS, mask classes, counts, and historical comparison are retained in the JSONB `provenance`. `cloud_percentage` stores the scene-level cloud percentage from the imagery metadata; the cloud/shadow percentage within the water-body boundary is stored separately in provenance. The existing Numeric(14, 4) square-kilometre field rounds values to 0.0001 km², so `provenance.area.water_area_sq_m` is the more precise recorded result for smaller water bodies.

Historical comparisons use the latest earlier successful Sentinel-2 observation for the same water body only when processing version, MNDWI threshold, projected CRS, and pixel size match. If no compatible baseline exists, change fields are null. The processor rejects boundaries whose analysis grid would exceed five million pixels to bound memory use.

Only water bodies whose database status is `verified` and whose boundary is a non-empty Polygon or MultiPolygon may be processed. Preliminary, rejected, and boundary-less bodies are rejected. No boundary geometry is generated by this implementation.

## Existing schema constraint to resolve

The existing database schema has the global unique constraint `uq_satellite_scene(satellite, scene_id)`. A Sentinel-2 scene commonly overlaps more than one registered water body, but this constraint permits only one observation row for that satellite scene across the entire database. The persistence service detects a previously recorded scene and reports this conflict. Supporting the same source scene for multiple water bodies requires a reviewed migration to make uniqueness include `water_body_id`; that migration has not been created or run and should not be applied without schema approval.

## Configuration and dependencies

NumPy and Rasterio are declared in `backend/pyproject.toml` and installed with the normal backend project installation. Configure:

- `SATELLITE_MNDWI_WATER_THRESHOLD`: inclusive MNDWI cutoff in [-1, 1]; default `0.0` pending local calibration.
- `SATELLITE_ANALYSIS_PIXEL_SIZE_M`: projected grid size in metres; default `20`.

The processing tests use synthetic arrays and do not require a database. No live Sentinel imagery, API credentials, or example observations are included.

## Provider and API blocker

No imagery source has been selected and no provider credentials are configured. Copernicus Data Space documents a Sentinel-2 Level-2A STAC collection. If Sentinel Hub processing is selected, its documented API uses an OAuth client ID and secret. These credentials must be provisioned by the project owner and supplied through environment variables; none are assumed here. The current implementation provides only the provider contract and read-only history APIs. A live adapter and processing endpoint should follow after a provider, credentials/access policy, and imagery storage location are approved.

The current API has no background job system. Before exposing a live processing endpoint, decide whether bounded scene processing can run within request limits or should be dispatched through an approved job runner.
